–# 分布式、AI 原生操作系统：讨论记录

日期：2026-10-05 至 2026-10-06

本文整理了围绕"用 Rust 写一个新的操作系统，并实现分布式、AI 原生、一切皆插件"这一设想的完整讨论，包括每个问题、结论和后续建议。

---

## 1\. 用 Rust 写测试（学习）用操作系统：优缺点

### 优点

- **内存安全**：安全 Rust 消除了大部分 use-after-free、double-free、缓冲区溢出，这些恰恰是 xv6 风格 C 代码里最耗时的 bug。  
- **`unsafe` 被限制并可见**：OS 需要裸指针、MMIO、内联汇编、页表操作，在 Rust 里这些都集中在 `unsafe` 块中，出问题时容易定位，也可以把每个硬件原语包装成小而安全的 API。  
- **类型系统可编码内核不变量**：`PhysAddr`/`VirtAddr` 等 newtype 避免混用；所有权可以表达"一个物理页帧只属于一个页表"；`Mutex<T>` 守卫可以让"忘记持锁"变成编译错误。  
- **裸机生态较好**：`#![no_std]`、`riscv`/`x86_64` crate、`bitflags`、`tock-registers`、Cargo、Miri 等。  
- **现代语言特性**：带数据的枚举、`Result`/`Option`、trait 驱动抽象，使 VFS、系统调用分发等代码比 C 的函数指针表清晰。  
- **现实相关性**：Rust 已被 Linux 接受，Redox、Theseus、Tock、Asterinas 等项目证明可行。

### 缺点

- **学习曲线陡**：同时学借用检查器和调度、虚拟内存；侵入式链表、父子进程树、共享缓冲缓存等结构与所有权规则冲突，常被迫用 `unsafe` 或 `Rc`/`Arc`。  
- **大量代码仍是 `unsafe`**：上下文切换、陷阱处理、页表、DMA 都打破 Rust 的别名假设，而写出正确的 `unsafe` 比写 C 更难（UB 更隐蔽）。  
- **学习资料偏少**：MIT 6.1810、xv6 和多数教材以 C 为准，要自己做概念翻译。  
- **构建与工具链摩擦**：自定义 target、`-Zbuild-std`、nightly 特性、链接脚本、panic 与分配器处理；编译比 C 慢。  
- **抽象可能掩盖硬件**：对学习来说，C 的"结构体就是字节、锁就是一个自旋字"更能看清机制。  
- **并发只是部分解决**：Rust 防数据竞争，但防不了死锁、中断上下文 bug 和内存序错误。

### 建议路径

先完成 xv6-riscv 的 C 实验，理解内核在做什么；再用 Rust 逐块重写：启动 → 分配器 → 页表 → 陷阱 → 调度器 → 文件系统。参考：Blog OS（Philipp Oppermann）、rCore 教程、xv6-rust 移植。

## 2\. 作为真实产品：新写一个 Rust 操作系统是否合适

**结论：通用操作系统几乎总是坏主意；Rust 适合做，但"OS 本身"很少是值得做的部分。**

### 为什么通用 OS 不合适

- 驱动与硬件支持是最大成本（Wi-Fi、GPU、USB、NVMe、电源管理）。  
- 没有软件生态（浏览器、工具链、应用），没有 POSIX/Linux 兼容就从零开始；Redox、Fuchsia 是前车之鉴。  
- 安全与维护永无止境（CVE 响应、长期支持、认证、更新）。  
- Rust 只解决一小部分风险，最大风险仍是范围、硬件、生态和资金。

### 适合新 Rust OS 的场景

- 嵌入式/IoT、硬件固定（如 Tock、Hubris）。  
- 安全关键领域（汽车、航空、医疗、工业），需要认证（ISO 26262、DO-178C、IEC 61508），Ferrocene 可协助。  
- Hypervisor、unikernel、microVM guest。  
- 机密计算、安全飞地（可信代码基很小）。  
- 有长期资金的研究或战略性项目。

### 更好的替代路径

- 在 Linux 内核上做 Rust 组件或发行版。  
- 写 Rust 的 Linux 内核模块（已被官方支持）。  
- 以 Zephyr、seL4、Tock 为基础，只做差异化部分。  
- 针对特定负载的 Rust unikernel 或 hypervisor。

### 动手前要回答的问题

1. 新 OS 解决了什么 Linux/RTOS 解决不了的客户痛点？  
2. 硬件是否固定且可控？  
3. 是否需要 Linux/POSIX 应用兼容？  
4. 是否有 3 到 5 年无收入期的资金和团队？  
5. 是否需要安全认证，成本多少？

## 3\. 愿景：分布式、AI 原生的"一台计算机"

### 需求描述

登录后不用关心本地机器；任何机器上登录都能看到自己的文件、资源和工作平台；数据分布式存储在网络中，去掉任意一台机器信息仍可完整恢复；所有联网机器对用户来说是一台计算机，可用任意终端登录；AI 原生，尽量只靠与 AI 的对话完成目的。

### 前人探索

Plan 9 / Inferno（统一命名空间）、Amoeba / Sprite / LOCUS（单一系统映像）、Chromebook / Solid / Urbit（身份与设备分离）、IPFS / Tahoe-LAFS / Ceph（内容寻址分布式存储）。这些项目多数没有普及，原因多在生态、延迟和商业模式，而不是技术不可行。

### 区块链不是合适的工具

核心需求是冗余存储，不需要全局共识：

| 需求 | 更合适的技术 |
| :---- | :---- |
| 数据冗余、可恢复 | 纠删码（Reed-Solomon）加多副本：Ceph、Tahoe-LAFS、IPFS/Filecoin |
| 多终端同步、离线合并 | CRDT（Automerge、Yjs）、Merkle DAG |
| 身份与登录 | 公私钥、DID、Passkey |
| 隐私 | 客户端端到端加密，节点只看到密文 |
| 版本历史、防篡改 | 内容寻址的 Merkle 树（Git 式） |

区块链最多可用于：陌生人提供存储并付费的激励机制。仅在自己的设备和云服务器之间同步，则不需要。

### 分层架构

1. **身份与密钥层**：主密钥控制一切；需要设计密钥丢失后的恢复方案（社交恢复、多重签名）。  
2. **存储层**：加密的内容寻址对象存储，加纠删码和跨节点副本；本地保留热数据缓存，支持离线。  
3. **计算层**：任何机器可拉起用户的工作环境（容器或 microVM 加挂载存储），环境可迁移。  
4. **命名空间与权限层**：Plan 9 风格的统一资源视图；设备、应用、AI 代理只获得必要的 capability。  
5. **AI 代理层**：对话式意图入口。

内核无需重写，可跑在 Linux 上；Rust 适合写存储、同步、网络和权限这些守护进程。

### AI 原生部分要提前设计的问题

- **确定性与可审计**：每个操作有结构化记录，可回放、可撤销；存储层的版本化可提供回滚。  
- **权限与提示注入**：代理在 capability 模型下运行，高风险操作（删除、转账、外发）需确认。  
- **本地与云端模型路由**：隐私敏感数据用本地小模型，复杂任务用云端模型。  
- **不要完全取消界面**：对话适合表达意图，精确编辑有时直接操作更快；可以让 AI 生成临时界面。

### 主要风险

- 延迟与带宽（编译大项目、看视频时文件在网络上）。  
- 离线与弱网：应以本地优先（local-first）为原则。  
- 在不可信终端上登录的安全问题：需要受信任设备、临时会话、硬件密钥等分级机制。  
- 运维成本：个人用容易，多用户、可靠、可计费的服务难得多。

### 建议的推进顺序

1. MVP（几个月）：用现有开源组件做"个人云工作区"，3 到 5 台自己的机器组成集群，验证"拔掉一台能完整恢复"和"任意终端登录到同一环境"。  
2. 加入 AI 代理：接 MCP 等工具协议，通过 capability 操作存储与计算，做好审计和回滚。  
3. 验证用户价值：先自用，再给小团队用。  
4. 之后再考虑：自研内核、多用户、去中心化激励、区块链。

## 4\. "一切皆插件"与可热插拔的微内核

### 关于参考论文

arXiv 2608.25512《A Programming Paradigm for Spatiotemporal Composability》（据摘要）讨论**编程语言层面的动态组合**：提出"可撤销副作用"（revertible effects，组件卸载时撤销其影响）和"响应式协效应"（reactive coeffects，组件对环境依赖的声明与动态解析），并实现为 Cordis 框架，带热模块替换。

**论文没有讨论内核或操作系统**，把它用于 OS 是自己的延伸；以上内容仅基于摘要级别，未读全文。

两个概念在 OS 中的对应：

- 可撤销副作用 ↔ 卸载驱动或服务后回收内存、句柄、中断、定时器，撤销授予他人的权限。  
- 协效应 ↔ 组件声明所需 capability，由系统运行时提供、替换或撤销。

### 三个层次的可行性

| 层次 | 可否热插拔 | 先例 |
| :---- | :---- | :---- |
| 驱动、文件系统、网络栈、服务（微内核之外） | 成熟可行 | MINIX 3、QNX、Fuchsia 组件、Genode、Erlang 热代码加载 |
| 调度、内存等内核内部策略模块 | 可行，需精心设计接口 | Linux 内核模块、eBPF、sched\_ext、Theseus OS |
| 微内核核心本身（地址空间、IPC、能力、基本调度） | 理论可行，实践很难 | Ksplice/kpatch 式热补丁、Theseus 部分实验；seL4 刻意保持不变 |

### 真正的难点

1. **状态迁移**：新旧模块间转移进行中的 IPC、锁、等待线程，最容易出错。  
2. **硬件副作用不可撤销**：DMA 已写数据、设备寄存器状态、已发网络包无法回滚。  
3. **能力撤销与悬挂引用**：卸载模块时，别人手里的 capability 必须失效。  
4. **接口与 ABI 稳定性**：Rust 没有稳定 ABI，跨版本插件需自定义接口（WIT/WASM 组件模型或自定义 IPC）。  
5. **信任基**：微内核价值在于小而稳定，可审计甚至形式化验证；让内核本身可热换会扩大攻击面。  
6. **IPC 性能**：一切皆插件意味着频繁跨隔离边界，需要快速 IPC 与零拷贝。

### 设计建议

- 追求"**内核极小、几乎不变，其余一切皆插件，且插件有统一生命周期**"，而不是内核可热插拔。  
- 底层选现有微内核；插件层用 WASM 组件模型（Wasmtime）或进程级隔离，插件声明所需 capability，卸载时自动撤销权限与资源。  
- 存储后端、网络协议、调度策略、AI 代理工具都做成插件；换内核时用"检查点加状态迁移加重启"。  
- 结论：**"一切皆插件"作为用户态系统架构原则很合适；"微内核本身热插拔"更适合作为后期研究课题。**

### 可做的小实验

用 Rust 加 Wasmtime 做一个插件宿主，定义 capability 接口，实现"加载、使用、卸载、自动回收资源"的完整生命周期，看该模型能否承载存储与 AI 代理两类插件。

## 5\. 宿主微内核选型：推荐 seL4

### 推荐理由

1. **能力模型原生**：所有访问权限都是 capability，可委派、收回、细粒度限制，正好对应"插件声明依赖、卸载自动撤销"。  
2. **内核小且经形式化验证**：核心约一万行，功能正确性与隔离性有机器检查的证明；对"任意终端登录、AI 代理代操作"的愿景，信任根最扎实。  
3. **Rust 用户态支持持续推进**：2026 年 7 月 seL4 官方发布了 seL4 16.0.0、Microkit 2.3.0、CAmkES 3.13.0、capDL 0.6.0、rust-sel4 5.0.0。  
4. **许可与治理友好**：内核 GPLv2，用户态库多为 BSD，由 seL4 基金会维护，不依赖单一公司。  
5. **理念一致**：驱动、文件系统、网络栈都在用户态，崩溃不会拖垮内核。

### 要正视的代价

- 它只是内核，没有现成的文件系统、网络栈、POSIX 层、图形栈，需自建或接入 Genode、LionsOS 等项目。  
- 硬件支持窄（支持 ARM、RISC-V、x86\_64，但真实硬件驱动覆盖有限）；覆盖"任意终端"通常要在 seL4 上用虚拟机运行 Linux 客户机。  
- Microkit/CAmkES 的系统描述偏静态，运行时加载与卸载要在自己的根任务或服务管理器里实现，这正是"热插拔"的核心工作。  
- 学习曲线陡，用户态调试比 Linux 复杂。

### 备选方案对比

| 候选 | 优势 | 不选的原因 |
| :---- | :---- | :---- |
| Zircon（Fuchsia） | 对象加句柄的能力模型，组件框架成熟，动态组件加载是一等特性 | 未能查到 2026 年其在 Google 之外的可靠使用情况，生态与治理方向不明朗 |
| Redox | 纯 Rust，社区活跃 | 成熟度和安全论证不如 seL4，无形式化验证 |
| Theseus | 最贴近运行时热替换内核组件的研究 | 偏研究原型，不适合直接承载产品 |
| Asterinas | Rust，兼容 Linux 接口，迭代快 | 是 framekernel 而非微内核，隔离模型不同 |
| Linux 加用户态插件层 | 硬件与生态最全，上手最快 | 内核大、信任基大，与微内核目标不一致 |

### 分阶段落地

1. **第一阶段**：在 Linux 用户态做插件宿主（Rust 加 Wasmtime 组件模型），跑通 capability 接口、生命周期、资源自动回收；这些设计与宿主无关。  
2. **第二阶段**：把同一套接口移植到 seL4，capability 映射到 seL4 原生 capability，Linux 作为客户机提供硬件兼容。  
3. **第三阶段**：逐步用原生 seL4 组件替换 Linux 客户机承担的功能。

## 6\. 总体结论与下一步

- 通用 OS 作为产品风险极高；这个愿景更现实的形态是"**Linux 或 seL4 之上的分布式、AI 原生个人工作区**"，核心价值在存储、同步、身份、capability 与 AI 代理。  
- 区块链非必需；用纠删码、内容寻址、CRDT、端到端加密实现可恢复与一致。  
- 采用"内核极小且稳定，其余皆插件"的架构，以 capability 作为统一的权限与生命周期机制。  
- 宿主选 seL4 作为长期目标，但先在 Linux 用户态验证插件模型。

### 可继续推进的事项

1. 设计第一阶段插件接口：capability 定义、插件清单格式、加载与卸载流程。  
2. 画出分层架构图。  
3. 把 MVP 拆成技术选型与里程碑。
